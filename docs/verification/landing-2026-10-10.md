## What a phone could talk to

The existing server/API handles bots and chats, provider status and models, memory files and Changes history, routines and results, and authorized report reads/downloads. A future phone client could use those boundaries while preserving authorization, memory hash/conflict checks and report access tied to its conversation and message. That would still require a phone interface and a secure connection to the server; no phone integration is verified here.

Provider CLIs, credentials, browser profiles, local files and scheduled work belong to the machine running the server. A phone would not itself run the Mac's Claude/Codex subscription tools or inherit their saved logins. Electron windows/preload, OS credential storage, desktop control and the current local PDF Save flow depend on the desktop app. Remote access also depends on that host remaining reachable and able to run the work. These are existing boundaries, not a new iOS implementation or a shared credential-vault claim.
